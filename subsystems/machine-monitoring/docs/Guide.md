# Machine Monitoring Subsystem
## Smart Factory Project — Embedded Systems Course

---

## 1. معرفی پروژه

این زیرسیستم بخشی از پروژه‌ی کلی **کارخانه‌ی هوشمند (Smart Factory)** است که شامل چهار زیرسیستم زیر می‌باشد:

- **machine-monitoring** ← این بخش
- workforce-management
- quality-control
- fire-system

هدف این زیرسیستم، **پایش لرزش ماشین‌آلات صنعتی** به صورت بلادرنگ (Real-Time) است. سیستم با خواندن سیگنال آنالوگ از یک سنسور لرزش (در شبیه‌سازی: پتانسیومتر)، وضعیت ماشین را تحلیل کرده و از طریق LCD، LED (وضعیت + نوار شدت) و UART به اپراتور اطلاع می‌دهد.

## 4. معماری نرم‌افزار

### 4.1 ماژول‌های نرم‌افزاری

```
WithProteus8/
├── Core/
│   ├── Inc/
│   │   ├── main.h
│   │   └── lcd.h          ← درایور LCD (نوشته شده توسط توسعه‌دهنده)
│   └── Src/
│       ├── main.c          ← منطق اصلی سیستم
│       ├── lcd.c           ← پیاده‌سازی درایور LCD
│       └── stm32f1xx_hal_...← درایورهای HAL (تولید CubeMX)
└── Drivers/
    └── STM32F1xx_HAL_Driver/
```

### 4.2 پریفرال‌های پیکربندی‌شده

**ADC1:**
- حالت: Continuous Conversion، تک‌کاناله
- کانال: IN0 (PA0)
- تریگر: Software Start
- تراز داده: Right-aligned
- دقت: 12-bit

**USART1:**
- Baud Rate: 115200
- Data Bits: 8
- Stop Bits: 1
- Parity: None
- Mode: TX/RX

**GPIO:**
- PB0, PB1: Output Push-Pull (LED وضعیت)
- PB3–PB8: Output Push-Pull (LCD)
- PB10–PB13: Output Push-Pull (نوار LED شدت)

**Clock:**
- منبع: HSI (Internal 8 MHz)
- PLL: غیرفعال
- ADC Clock: PCLK2 / 2

## 5. منطق سیستم

### 5.1 فلوچارت کلی

```
START
  │
  ▼
راه‌اندازی HAL، ADC، UART، GPIO
  │
  ▼
نمایش "Smart Factory / Initializing..." روی LCD
  │
  ▼
HAL_Delay(2000ms)
  │
  ▼
┌─────────────────────────────────┐
│           حلقه اصلی             │
│                                 │
│  خواندن ADC (PA0)               │
│         │                       │
│  تبدیل به mm/s                  │
│  vib = (adc × 140) / 4095       │
│         │                       │
│  ┌──────┴──────┐                │
│  │  آپدیت نوار  │                │
│  │  LED شدت     │                │
│  └──────┬──────┘                │
│         │                       │
│  ┌──────┴──────┐                │
│  │  تعیین Zone │                │
│  └──────┬──────┘                │
│    NORMAL│WARNING│DANGER         │
│         │                       │
│  ارسال UART + کنترل LED + LCD   │
│                                 │
└─────────────────────────────────┘
```

### 5.2 استاندارد آستانه‌گذاری (ISO 10816-3)

این استاندارد برای ماشین‌آلات صنعتی متوسط (موتور، پمپ، کمپرسور) تعریف شده است:

| Zone | محدوده (mm/s) | مقدار ADC | وضعیت LED | پیام LCD | اقدام |
|------|--------------|-----------|-----------|----------|-------|
| A | 0.0 – 2.8 | 0 – 818 | سبز ثابت | NORMAL | ادامه کار |
| B | 2.8 – 7.1 | 819 – 2073 | قرمز آهسته (500ms) | WARNING! | بررسی دوره‌ای |
| C | > 7.1 | 2074 – 4095 | قرمز سریع (100ms) | DANGER!! | توقف فوری |

### 5.3 فرمول تبدیل ADC به mm/s

```
vib_scaled = (ADC × 140) / 4095

vib_int = vib_scaled / 10        ← قسمت صحیح
vib_dec = vib_scaled % 10        ← قسمت اعشاری

مثال: ADC = 2048
vib_scaled = (2048 × 140) / 4095 = 70
vib_int = 7, vib_dec = 0
نتیجه: 7.0 mm/s → DANGER
```

> **چرا از اعداد صحیح به جای float استفاده شد؟**
> محاسبات float روی STM32F103 (بدون FPU) می‌تواند باعث خطاهای تجمعی و Buffer Overflow در sprintf شود. استفاده از uint32_t و uint16_t محاسبات را دقیق‌تر و سریع‌تر می‌کند.

### 5.4 نوار LED شدت لرزش (Trend Bar)

به‌عنوان یک لایه‌ی نمایشی اضافه (مستقل از NORMAL/WARNING/DANGER)، چهار LED به‌صورت پلکانی روشن می‌شوند تا شدت لرزش را به‌صورت بصری و سریع (مثل نشانگر آنتن موبایل) نشان دهند:

| آستانه (vib_scaled) | معادل mm/s | LED های روشن |
|---------------------|------------|----------------|
| ≥ 10 | ≥ 1.0 | LED1 |
| ≥ 35 | ≥ 3.5 | LED1, LED2 |
| ≥ 70 | ≥ 7.0 | LED1, LED2, LED3 |
| ≥ 105 | ≥ 10.5 | LED1, LED2, LED3, LED4 |

```c
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_10, (vib_scaled >= 10)  ? GPIO_PIN_SET : GPIO_PIN_RESET);
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_11, (vib_scaled >= 35)  ? GPIO_PIN_SET : GPIO_PIN_RESET);
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_12, (vib_scaled >= 70)  ? GPIO_PIN_SET : GPIO_PIN_RESET);
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_13, (vib_scaled >= 105) ? GPIO_PIN_SET : GPIO_PIN_RESET);
```

این بخش عمداً **بدون Delay و بدون محاسبات سنگین** پیاده‌سازی شد تا هیچ تأثیری روی سرعت شبیه‌سازی در پروتئوس نگذارد (درس گرفته‌شده از چالش‌های بخش ۷).

## 6. درایور LCD (خلاقیت پروژه)

یکی از بخش‌های خلاقانه‌ی این پروژه، نوشتن **درایور LCD سفارشی** برای LCD 16x2 در حالت 4-bit است. این درایور از صفر نوشته شد و شامل توابع زیر است:

```c
void LCD_Init(void);                           // مقداردهی اولیه
void LCD_Clear(void);                          // پاک کردن صفحه
void LCD_SetCursor(uint8_t row, uint8_t col);  // تنظیم موقعیت
void LCD_Print(char *str);                     // چاپ رشته
```

**چرا 4-bit به جای 8-bit؟**

در حالت 8-bit، به 8 پایه‌ی داده نیاز داریم که با توجه به تعداد محدود GPIO های موجود (که برخی برای LED و ADC اشغال شده بودند)، امکان‌پذیر نبود. در حالت 4-bit فقط 4 پایه‌ی داده (D4-D7) و 2 پایه‌ی کنترلی (RS، EN) کافی است.

**مکانیزم ارسال داده:**

```
یک بایت = دو nibble (4 بیت)
ابتدا 4 بیت بالا → پالس EN
سپس  4 بیت پایین → پالس EN
```

## 7. چالش‌ها و راه‌حل‌ها

### چالش 1: خطای شبیه‌سازی "VCC and GND nets are connected"

**مشکل:** پروتئوس پایه‌های مخفی VDDA و VSSA میکروکنترلر را به یک نت مشترک وصل کرده بود.

**راه‌حل:** در پنجره‌ی Edit Component → Hidden Pins، مقادیر زیر تنظیم شد:
```
Pin VDD  → VDD (+3.3V)
Pin VDDA → VDD (+3.3V)
Pin VSS  → GND
Pin VSSA → GND
```

### چالش 2: خطای کامپایلر ARM Compiler V5

**مشکل:** پروژه برای ARM Compiler V5 تنظیم شده بود اما فقط V6.24 نصب بود.

**راه‌حل:** در Keil → Options for Target → ARM Compiler، گزینه‌ی "Use default compiler version 6" انتخاب شد.

### چالش 3: اعداد اشتباه روی LCD

**مشکل:** LCD اعداد عجیب مثل `36121776` نشان می‌داد در حالی که UART درست بود.

**علت:** `char msg[20]` برای رشته‌ی خروجی کوچک بود و Buffer Overflow حافظه‌ی متغیرهای `vib_int` و `vib_dec` را خراب می‌کرد.

**راه‌حل:** اندازه‌ی buffer به `char msg[40]` افزایش یافت و محاسبات از float به integer تغییر کرد.

### چالش 4: شروع ADC از عدد غیرصفر

**مشکل:** وقتی پتانسیومتر روی 0% بود، ADC مقدار ~300 می‌خواند نه 0.

**علت:** مقاومت داخلی پتانسیومتر در پروتئوس یک ولتاژ کوچک ایجاد می‌کند.

**راه‌حل:** استفاده از محاسبات integer که این offset جزئی را در نمایش تأثیر قابل توجهی نمی‌دهد.

### چالش 5: از دست رفتن تنظیمات Hidden Pins

**مشکل:** هر بار که قطعه‌ی جدیدی به شماتیک اضافه می‌شد، تنظیمات Hidden Pins ریست می‌شد.

**راه‌حل:** استفاده از نام استاندارد **VDD** (به جای +3.3V) که پروتئوس آن را به صورت دائمی در فایل پروژه ذخیره می‌کند.

### چالش 6: توسعه‌ی دو-دستگاهی و افت شدید سرعت شبیه‌سازی

**تلاش:** برای شبیه‌سازی مانیتورینگ دو دستگاه هم‌زمان، یک کانال ADC دوم (PA1، Scan Mode) و یک LCD 20x4 (به‌جای 16x2) اضافه شد تا وضعیت هر دو دستگاه، زمان کارکرد (Runtime)، و وضعیت سرویس دوره‌ای نمایش داده شود.

**مشکل:** پروتئوس با ترکیب «Scan Mode دو کاناله + LCD 20x4 + چند HAL_Delay پیاپی» دیگر نمی‌توانست در زمان واقعی (Real Time) اجرا شود؛ راه‌اندازی سیستم به بیش از ۱۰ ثانیه رسید و به‌روزرسانی دو کانال به‌صورت ناهمگام و با تأخیر محسوس انجام می‌شد.

**تحلیل علت:** این کندی ناشی از محدودیت **موتور شبیه‌سازی SPICE-based پروتئوس** بود، نه ضعف کد؛ محاسبه‌ی هم‌زمان رفتار آنالوگ دو کانال ADC به‌همراه رندر یک LCD بزرگ‌تر، بار پردازشی شبیه‌ساز را به‌شدت افزایش می‌دهد.

**تصمیم مهندسی:** به‌جای صرف زمان زیاد برای بهینه‌سازی یک شبیه‌سازی که در سخت‌افزار واقعی اصلاً مشکلی نداشت، تصمیم گرفته شد به نسخه‌ی پایدار **تک‌سنسور + LCD 16x2** بازگشته و ایده‌ی دو-دستگاهی به بخش «توسعه‌های آینده» منتقل شود (بخش ۹). این تصمیم نمونه‌ای از **مدیریت ریسک در پروژه‌های زمان‌محدود** است.

### چالش 7: عدم پخش صدا در Buzzer شبیه‌سازی‌شده

**تلاش:** برای هشدار صوتی در وضعیت DANGER، یک Buzzer روی پایه‌ی PB2 اضافه شد.

**مشکل اول:** مدل Buzzer انتخابی ولتاژ کاری **12V** داشت در حالی‌که پایه‌ی GPIO میکروکنترلر فقط 3.3V فراهم می‌کند؛ در نتیجه پایه به‌جای HIGH/LOW واضح (قرمز/آبی در پروتئوس)، رنگ **خاکستری** (ولتاژ نامشخص) نشان می‌داد.

**علت فنی:** بار Buzzer با مقاومت داخلی ۱۲Ω در ولتاژ ۳.۳ ولت جریانی حدود ۲۷۵mA می‌طلبد که به‌مراتب فراتر از توان خروجی پایه‌ی GPIO (حدود ۲۰-۲۵mA) است — دقیقاً همان مشکلی که در سخت‌افزار واقعی هم رخ می‌دهد و راه‌حل آن استفاده از یک ترانزیستور درایور (مثل BC547/2N2222) بین میکروکنترلر و بار پرمصرف است.

**مشکل دوم:** حتی پس از رفع مشکل ولتاژ، پروتئوس **صدای واقعی از Buzzer پخش نمی‌کند** چون این نرم‌افزار یک شبیه‌ساز الکترونیکی است، نه شبیه‌ساز صوتی.

**تصمیم نهایی:** به‌جای اضافه کردن یک زیرمدار ترانزیستوری صرفاً برای یک اثر صوتی که در پروتئوس قابل شنیدن نیست، این ویژگی به بخش «توسعه‌های آینده» منتقل شد. **اثبات صحت منطق هشدار** از طریق مشاهده‌ی چشمک‌زدن سیگنال دیجیتال روی پایه‌ی PB2 در حالت DANGER ارائه شد که نشان می‌دهد سیگنال کنترلی لازم برای فعال‌سازی یک Buzzer واقعی به‌درستی تولید می‌شود.

## 8. خلاقیت‌های پروژه

### 8.1 درایور LCD سفارشی (4-bit Mode)
به جای استفاده از کتابخانه‌های آماده، درایور LCD از صفر نوشته شد. این کار باعث درک عمیق‌تر پروتکل ارتباطی LCD و صرفه‌جویی در پایه‌های GPIO شد.

### 8.2 محاسبات Integer به جای Float
برای جلوگیری از خطاهای ممیز شناور (که روی STM32F103 بدون FPU رایج است)، تمام محاسبات با اعداد صحیح انجام شد:
```c
uint16_t vib_scaled = (uint16_t)(((uint32_t)adc * 140) / 4095);
```

### 8.3 آستانه‌گذاری مبتنی بر استاندارد صنعتی
به جای تعریف دلخواه آستانه‌ها، از استاندارد **ISO 10816-3** استفاده شد که اعتبار علمی و صنعتی دارد.

### 8.4 سیستم هشدار چندلایه
چهار سطح نمایش هم‌زمان و مستقل:
- **بصری وضعیت:** LCD (متن) + دو LED رنگی (سبز/قرمز با الگوی چشمک متفاوت)
- **بصری شدت:** نوار ۴تایی LED که شدت لرزش را پلکانی نشان می‌دهد (مستقل از Zone بندی)
- **سریال:** UART برای مانیتورینگ از راه دور

### 8.5 پیام راه‌اندازی (Boot Screen)
نمایش "Smart Factory / Initializing..." هنگام روشن شدن سیستم که حس یک محصول حرفه‌ای را می‌دهد.

### 8.6 مدیریت ریسک مهندسی
در مواجهه با محدودیت‌های شبیه‌ساز (چالش‌های ۶ و ۷)، به‌جای اصرار بر تکمیل یک ویژگی پرریسک نزدیک به ددلاین، تصمیم آگاهانه به بازگشت به نسخه‌ی پایدار و مستندسازی ایده برای توسعه‌ی آتی گرفته شد — یک مهارت مهندسی واقعی، نه صرفاً یک محدودیت فنی.

## 9. توسعه‌های آینده (Future Work)

این موارد طراحی و تا حدی پیاده‌سازی شدند اما به دلیل محدودیت‌های شبیه‌ساز پروتئوس (نه محدودیت سخت‌افزار واقعی) به نسخه‌ی نهایی اضافه نشدند:

**۹.۱ مانیتورینگ چند دستگاهی:** استفاده از کانال دوم ADC (PA1) برای پایش هم‌زمان دستگاه دوم، با نمایش روی LCD 20x4 شامل:
```
Runtime: 0128s
M1: 3.5 mm/s  OK
M2: 8.1 mm/s  DANGER!!
Service: OK
```

**۹.۲ سرویس دوره‌ای بر اساس ساعت کارکرد:** شمارش زمان کارکرد سیستم (Running Hours) به‌جای تاریخ تقویمی (که نیاز به RTC با باتری backup دارد) و اعلام هشدار "SERVICE DUE" پس از عبور از آستانه‌ی از پیش تعیین‌شده — این رویکرد دقیقاً مطابق روش **نگهداری پیشگیرانه‌ی صنعتی (Preventive Maintenance)** است.

**۹.۳ هشدار صوتی (Buzzer):** افزودن یک ترانزیستور درایور (BC547/2N2222) برای کنترل Buzzer های با ولتاژ کاری بالاتر از خروجی GPIO، قابل پیاده‌سازی کامل روی سخت‌افزار واقعی (Blue Pill).

**۹.۴ در نظر گرفته شده برای پیاده‌سازی روی سخت‌افزار واقعی:** با توجه به اینکه محدودیت مشاهده‌شده صرفاً مربوط به کارایی شبیه‌ساز پروتئوس بود، تمام این ویژگی‌ها روی برد فیزیکی STM32F103C8T6 (Blue Pill) بدون مشکل کارایی قابل اجرا هستند.
